## 2. Technical errors

- §2.1 (line 44): "on a **bound or pending claim** only `spec.resources.requests.storage` can change" is wrong.
  The update validator forgives a `requests["storage"]` diff only when `status.phase == Bound`; on a Pending
  claim the whole spec is immutable — the API answer is
  `Forbidden: spec is immutable after creation except resources.requests and volumeAttributesClassName for bound claims`.
  Two related omissions: an unbound claim CAN have `spec.volumeName` set once (when previously empty — a real fix
  tool the lesson denies), and a bound claim can also change `spec.volumeAttributesClassName` (VAC is on in v1.37).
- §2.1 (line 44) and §7.3: "the volume source, `capacity` and `nodeAffinity` cannot [be patched]" / Hint 2's
  "`capacity` is immutable on a PV" is wrong. `ValidatePersistentVolumeUpdate` checks only
  `persistentVolumeSource`, `volumeMode`, and `nodeAffinity` (the last only once set — it can be added when
  absent). `spec.capacity` IS patchable — that is exactly what the expand controller writes after controller
  resize, and the documented manual-resize path edits PV capacity by hand. This also undercuts 7.3's stated
  rationale: patching `bf-c` to 3Gi is a legitimate (arguably too easy) alternative fix that verification OK5
  would accept. The correct fix teaching "the cluster is out of storage → provision a new PV" is still right,
  but for the true reason: inflating declared capacity lies about real backing storage, not because the field
  is immutable.

## 3. Labs

- §5 step 4 and §7.1 share a structural flaw: the persistence demos are scheduling lotteries. `w-pod2` /
  `reader` can land on the other worker, where the node-local `hostPath` directory is empty —
  `cat /data/note.txt` fails and verification OK4 fails for a reason unrelated to the lesson. Roughly 50%
  failure on the 2-worker kind cluster; nothing pins the replacement Pod to the writer's node.
- §7.2(d): `fixed` (`storageClassName: ""`, no static PV in the lab) stays `Pending`, so the resize patch is
  rejected with the immutability error above — not the documented `only dynamically provisioned pvc can be
  resized and the storageclass that provisions the pvc must support resize` shown as expected output. The
  `grep -q 'forbidden'` check passes either way, but the captured evidence teaches a different error than the
  lab intends; `fixed` must be Bound to a static PV first to demonstrate the documented rejection.
- Lab order stated, `break.sh` has no fault-naming comments, all verifications can fail, cleanups return to
  baseline. Otherwise sound.
