## 1. Why this matters

In real clusters nobody pre-creates a PersistentVolume for every application. An administrator installs one provisioner and one or more StorageClasses, and every claim then gets a fresh PV and real backing storage on demand. If you do not know this layer you cannot answer the most common storage tasks: create a class, make it the default, and prove that a claim provisions through it. It is also where silent failures live. A claim whose class names a provisioner that does not exist waits forever. Two default classes make claims land in a class you did not pick. And the default reclaim policy of a dynamic volume is `Delete`, so removing one claim can destroy the data for good.

## 2. Concepts

### 2.1 Static vs dynamic provisioning

In **static** provisioning ([T4.15](../part4-cka/T4.15-manage-persistent-volumes-and-persistent-volume.md)) you write the PV object yourself first; a claim only binds to a PV that already exists. In **dynamic** provisioning you create a **StorageClass** (SC) once. When a claim names that class, a **provisioner** (a controller outside `kube-controller-manager`) creates the real storage (a disk, a directory, an NFS export) and the matching PV object, and the PV controller binds them. The administrator writes one class; the cluster does the per-app work.

A claim picks its class with `spec.storageClassName`. Three cases, and the difference matters:

| `storageClassName` on the PVC | Effect |
|---|---|
| `"fast-local"` (a name) | Use that class. If no class object has that name, the claim stays `Pending`. |
| `""` (empty string, explicit) | No class. Static binding only: the claim can only bind to a PV whose `storageClassName` is also `""`. Dynamic provisioning is off for this claim. |
| field omitted | The **default** StorageClass is assigned (see 2.4). If no default exists, the claim behaves like `""`. |

### 2.2 The StorageClass object

A StorageClass is cluster-scoped (`apiVersion: storage.k8s.io/v1`, kind `StorageClass`). It is a recipe: **who** creates volumes (`provisioner`), **how** (`parameters`), and which fields the created PVs get.

| Field | Default | What it does | Mutable after creation? |
|---|---|---|---|
| `provisioner` | none (required) | Name of the provisioner that creates volumes for this class. | No — rejected by the API. |
| `parameters` | `{}` | Free-form `key: value` strings passed to the provisioner; the driver defines the keys. | No |
| `reclaimPolicy` | `Delete` | `persistentVolumeReclaimPolicy` stamped on every PV the class creates. `Delete` or `Retain`. | No, once set (see To verify) |
| `volumeBindingMode` | `Immediate` | `Immediate` = provision as soon as the claim exists; `WaitForFirstConsumer` = wait until a Pod using the claim is scheduled. | No, once set (see To verify) |
| `allowVolumeExpansion` | `false` | Lets claims of this class grow via a PVC edit (driver must support resize). | Yes (patch) |
| `mountOptions` | none | Mount flags copied to every created PV. Not validated. | Yes (see To verify) |
| `allowedTopologies` | none = all | Restricts provisioning to nodes matching topology labels (for example a zone). | No |

Only `allowVolumeExpansion`, `mountOptions` and metadata (labels, annotations) can be changed on an existing class; everything else is immutable, so a wrong `provisioner` means delete and recreate the class. The exact list of mutable fields is in To verify.

**provisioner.** A string that must match a provisioner running in or for the cluster. Values you will meet:

- In-tree `kubernetes.io/*` names were the old internal provisioners (for example `kubernetes.io/aws-ebs`). The cloud ones are removed; their CSI drivers replaced them. `kubernetes.io/no-provisioner` is still used as a sentinel meaning "nobody provisions; the admin creates PVs by hand" — that is how the static local-volume class in [T4.14](../part4-cka/T4.14-configure-volume-types-access-modes-and.md) and [T4.15](../part4-cka/T4.15-manage-persistent-volumes-and-persistent-volume.md) works.
- An external provisioner name chosen by its author, for example `rancher.io/local-path`.
- A CSI driver name, for example `ebs.csi.aws.com`, `hostpath.csi.k8s.io`, `nfs.csi.k8s.io`. The driver's name *is* the provisioner name.

A typo here is silent: nothing complains at apply time, the claim just waits forever (section 6).

**parameters.** Whatever the driver accepts — the API server does not check the keys. For AWS EBS CSI you might see `type: gp3`, `iopsPerGB: "50"`, `encrypted: "true"`. For the NFS CSI driver, `server` and `share`. `rancher.io/local-path` accepts a `parameters` block but mostly ignores it; its behavior is configured by its own ConfigMap (see 2.5). A wrong key makes `CreateVolume` fail, which you see in the provisioner's logs, not in `k get sc`.

**reclaimPolicy.** Copied to every PV the class creates. `Delete` (the default) destroys the backing storage when the claim is deleted (see 2.8). `Retain` keeps the PV and the data for manual reclaim. The `Recycle` policy is not valid here.

**volumeBindingMode.** See 2.3 — this field decides whether provisioning waits for the Pod.

**allowVolumeExpansion.** When `true`, you can edit a bound claim's `spec.resources.requests.storage` to a larger value and the driver resizes the volume. You can never shrink. The flag alone is not enough — the driver must implement resize. `rancher.io/local-path` does not support expansion (a directory has nothing to resize; listed in To verify for v0.0.37), so the labs create classes with the flag `true` to show the field, not to resize.

**mountOptions.** Passed through to the created PV's `mountOptions`. Not validated: a bad option only surfaces as a mount error when a Pod starts. Only meaningful for volume types that honor mount options (NFS, CSI drivers that implement them).

**allowedTopologies.** A list of `nodeSelectorTerms` over node topology labels such as `topology.kubernetes.io/zone` or `kubernetes.io/hostname`. It limits where volumes may be provisioned. Example: a class with `allowedTopologies` matching only `zone-a` will not create a volume in `zone-b`. Combined with `WaitForFirstConsumer` the scheduler picks a node inside the allowed topologies and the volume lands there (see 2.3).

### 2.3 volumeBindingMode: Immediate vs WaitForFirstConsumer

| | `Immediate` (default) | `WaitForFirstConsumer` (WFFC) |
|---|---|---|
| When the volume is created | As soon as the claim exists | Only after a Pod that uses the claim is scheduled |
| Claim state right after creation | `Pending` briefly, then `Bound` | `Pending` with event reason `WaitForFirstConsumer` — stays until a Pod exists |
| Where the volume lands | Wherever the provisioner chooses; for node-local storage possibly the wrong node | On / reachable from the node the scheduler picked for the Pod |
| Use for | Network storage reachable from every node (NFS, cloud disks in one-zone clusters) | Anything node-local (local-path, `local` PVs) and zone-aware disks |

Why WFFC exists: for storage that lives on one node, binding early is dangerous. With `Immediate`, the claim binds and the provisioner creates the volume on some node before the scheduler knows where the Pod goes — the Pod can then land on a different node and never mount the volume. With `WaitForFirstConsumer` the order flips: the scheduler first picks a node (respecting the Pod's constraints **and** the class's `allowedTopologies`), writes the annotation `volume.kubernetes.io/selected-node` on the claim, and only then does the provisioner create the volume for that node. That is **topology-aware provisioning**: the volume is created where the consumer actually is.

A `Pending` claim whose describe shows `WaitForFirstConsumer` is not broken. It is waiting for you to create the Pod.

### 2.4 The default StorageClass and DefaultStorageClass admission

A class becomes the default through an annotation on the class object:

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: my-class
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"   # the value is a string "true", not a boolean
provisioner: example.com/my-provisioner                   # placeholder name; use a real provisioner in practice
```

`k get sc` marks it with `(default)` after the name.

**The admission plugin.** `DefaultStorageClass` is one of the admission plugins enabled by default in `kube-apiserver`. It mutates PVCs at creation time: if a PVC has no `storageClassName` field at all, the plugin fills it with the name of the default class. It does not touch claims that name a class or explicitly set `storageClassName: ""`. Since v1.28 the mechanism is also **retroactive**: a PVC created while no default exists is updated later when a default class appears (behavior on 1.37 in To verify).

**Only one default.** The docs describe one default class per cluster. If several classes carry the annotation, a claim without a class gets the most recently created default — the other "defaults" are silently ignored for new claims (exact wording in the docs; listed in To verify). That is why switching the default is two patches: remove the annotation from the old class, add it to the new one, then check `k get sc` shows `(default)` exactly once.

The legacy annotation `storageclass.beta.kubernetes.io/is-default-class` is still honored; do not write it — use the stable name.

### 2.5 Provisioners you will meet in labs

| Provisioner | `provisioner` value | Type | What it creates | Where you get it |
|---|---|---|---|---|
| Rancher local-path | `rancher.io/local-path` | External provisioner (not CSI) | A hostPath PV per claim, directory under `/opt/local-path-provisioner` on the selected node, PV pinned to that node with `nodeAffinity` | Ships as class `standard` on kind; install on kubeadm from its manifest (Lab 7.1) |
| csi-driver-host-path | `hostpath.csi.k8s.io` | Real CSI driver with all sidecars | Host-path volumes through CSI calls; supports snapshots and expansion | kubernetes-csi example driver, deploy script |
| nfs-subdir-external-provisioner | configurable, e.g. `example.com/nfs` | External provisioner (project deprecated) | One subdirectory on an existing NFS export per claim — gives RWX | Helm chart / manifests; deprecated in favour of the CSI driver below |
| csi-driver-nfs | `nfs.csi.k8s.io` | Real CSI driver | Subdirectories on an NFS export through CSI — dynamic RWX | kubernetes-sigs csi-driver-nfs |
| (sentinel) | `kubernetes.io/no-provisioner` | None | Nothing — classes that only label static PVs | Built in |

**Rancher local-path-provisioner v0.0.37** is what the guide's VM cluster uses. Install it on kubeadm with:

```bash
k apply -f https://raw.githubusercontent.com/rancher/local-path-provisioner/v0.0.37/deploy/local-path-storage.yaml
```

That manifest creates the namespace `local-path-storage`, a ServiceAccount plus RBAC, Deployment `local-path-provisioner` (one replica, image `rancher/local-path-provisioner:v0.0.37`), ConfigMap `local-path-config` (its `nodePathMap` sets the per-node data directory, default `/opt/local-path-provisioner`), and a StorageClass named `local-path` with `volumeBindingMode: WaitForFirstConsumer` and `reclaimPolicy: Delete`. It is **not** a CSI driver: it is a standalone controller that shells out to helper Pods on the node to create and delete directories. Its created PVs use a node-local source pinned with `nodeAffinity` (hostPath in the versions this lesson assumes; whether v0.0.37 uses `hostPath` or `local` as the PV source is in To verify). On kind the same provisioner is preinstalled and the class is called `standard` and is already the default — its data directory there is `/var/local-path-provisioner` inside the node containers, not `/opt/local-path-provisioner`.

**Why labs use it and what to notice:** it is small, needs no cloud, and exercises the whole dynamic flow. The catch it teaches is real — node-local storage is why `WaitForFirstConsumer` exists.

### 2.6 Volume expansion in practice

If the class has `allowVolumeExpansion: true` and the driver implements resize, grow a claim by editing it:

```bash
k patch pvc data -n lab-t416 -p '{"spec":{"resources":{"requests":{"storage":"2Gi"}}}}'
```

The PVC's status conditions show the resize (`Resizing`, then `FileSystemResizePending` while the kubelet expands the filesystem); `k describe pvc` shows the events. Shrinking is always rejected. If the class does not allow expansion the API rejects the edit; if the driver cannot resize (local-path, hostPath), the claim sits in a resize state that never completes — there is nothing to resize a directory into. Verify the flag before you edit: `k get sc <name> -o jsonpath='{.allowVolumeExpansion}'` (empty output means `false`, the field default).

### 2.7 Reclaim on dynamic PVs: what `Delete` really does

A dynamically created PV is a normal PV — the reclaim rules of [T4.15](../part4-cka/T4.15-manage-persistent-volumes-and-persistent-volume.md) apply. The difference is who acts:

- `reclaimPolicy: Delete` (the class default): when the bound claim is deleted, the provisioner is asked to delete the backing storage (CSI `DeleteVolume`, or local-path's helper Pod removing the directory), then the PV object is deleted too. **The data is gone.** For local-path that means the directory under `/opt/local-path-provisioner` on the node is removed (exact cleanup behavior in To verify).
- `reclaimPolicy: Retain`: the PV goes `Released`, keeps `claimRef`, and keeps the data. Same manual reclaim as a static Retain PV: clean the storage, remove `claimRef` to reuse, or delete the PV object.

The trap is the default. A static PV you write by hand defaults to `Retain`; a class-created PV defaults to `Delete`. If a task says "the data must survive claim deletion", set `reclaimPolicy: Retain` **in the class** (affects PVs created afterwards) or patch the PV's `persistentVolumeReclaimPolicy` before deleting its claim.

### 2.8 StatefulSet volumeClaimTemplates

A StatefulSet can stamp one PVC per replica from a template — this is where dynamic provisioning earns its keep, because 20 replicas get 20 PVs without you writing 20 PV objects:

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: web
  namespace: lab-t416
spec:
  serviceName: web
  replicas: 3
  selector:
    matchLabels: {app: web}
  template:
    metadata:
      labels: {app: web}
    spec:
      containers:
      - name: c
        image: busybox:1.36
        command: ["sleep", "3600"]
        volumeMounts:
        - {name: data, mountPath: /data}
  volumeClaimTemplates:
  - metadata:
      name: data                              # becomes part of each claim's name
    spec:
      storageClassName: fast-local            # which class provisions each replica's PV
      accessModes: [ReadWriteOnce]
      resources:
        requests:
          storage: 100Mi
```

Claims are named `<template-name>-<sts-name>-<ordinal>`: `data-web-0`, `data-web-1`, `data-web-2`. Each binds its own PV through the class. Two rules that surprise people:

- The claims are **not** deleted when the StatefulSet or its Pods are deleted — data safety by design. The exception is `spec.persistentVolumeClaimRetentionPolicy` (GA since v1.32): set `whenDeleted` or `whenScaled` to `Delete` and the controller removes the template claims automatically when the StatefulSet is deleted or scaled down. The default `Retain` is the behavior this bullet describes. Reclaim `Retain`ed claims by hand (`k delete pvc data-web-0 data-web-1 data-web-2 -n lab-t416`), which then triggers the class's reclaim policy on the PVs.
- Scaling down removes Pods but keeps their claims; scaling back up reattaches the same claims, so a returning replica finds its old data.

### 2.9 VolumeAttributesClass (awareness)

A `VolumeAttributesClass` (GA since v1.34, `storage.k8s.io/v1`) holds driver-tunable settings (provisioned IOPS, throughput) that can be **changed on a live volume** by editing the claim's `spec.volumeAttributesClassName`. It complements the StorageClass: the class is fixed at provisioning time; the attributes class can be swapped later if the CSI driver implements `ModifyVolume`. Detail and YAML are in [T4.14](../part4-cka/T4.14-configure-volume-types-access-modes-and.md). For this lesson, recognise the `VOLUMEATTRIBUTESCLASS` column in `k get pv` output and do not confuse the two objects: one picks how a volume is *born*, the other tunes it while it lives.

### 2.10 Reading the provisioner: logs and events

When a dynamic claim is `Pending`, two places tell the story, in this order:

1. **The claim's events** — `k describe pvc <name> -n <ns>`:
   - `WaitForFirstConsumer  waiting for first consumer to be created before binding` — WFFC, create the Pod.
   - `ExternalProvisioning  waiting for a volume to be created, either by external provisioner "X" or manually created by system administrator` — repeated while the controller waits for provisioner `X` to act. If `X` is misspelled or its Pods are down, this message loops forever.
   - `Provisioning ... External provisioner is provisioning volume for claim ...` then `ProvisioningSucceeded  Successfully provisioned volume pvc-<uid>` — the healthy path, emitted by the provisioner itself.
   - `ProvisioningFailed ...` — the provisioner tried and failed; the message carries the driver's error (bad parameter, no capacity, permission).
2. **The provisioner's logs** — wherever the provisioner runs:
   - Rancher local-path: `k -n local-path-storage logs deploy/local-path-provisioner`
   - A CSI driver: find the controller Pods (`k get pods -A | grep <driver>`), then read the provisioner sidecar, for example `k -n <driver-ns> logs <controller-pod> -c csi-provisioner`
   - Look for lines about `CreateVolume`, `DeleteVolume`, and errors naming your claim (exact log wording in To verify).

Also check that the provisioner's Pods are running at all: `k -n local-path-storage get pods` or `k get pods -A | grep provisioner`. A `CrashLoopBackOff` or a missing Deployment explains `ExternalProvisioning` looping.

### 2.11 Under the hood

- **Admission.** On PVC creation the `DefaultStorageClass` plugin stamps `spec.storageClassName` with the default class when the field is absent. After that the claim is immutable in the ways that matter — class, modes and `volumeMode` cannot be edited.
- **Hand-off to the provisioner.** The persistent-volume controller (in `kube-controller-manager`) sees the claim and annotates it `volume.kubernetes.io/storage-provisioner: <provisioner name>`; that annotation is the signal the external provisioner watches for. The controller also emits the `ExternalProvisioning` event while it waits.
- **WFFC scheduling.** For a WFFC claim the scheduler treats the Pod as schedulable only where a volume could exist (the class's `allowedTopologies`). After picking a node it writes `volume.kubernetes.io/selected-node` on the claim; the provisioner reads it and creates the volume for that node.
- **Provisioning.** The external-provisioner (for CSI drivers, the `csi-provisioner` sidecar container; for local-path, its own controller) calls the driver's `CreateVolume`, then creates the PV object itself — with the `csi` source and `volumeHandle`, or a hostPath/local source plus `nodeAffinity` — and the PV controller binds claim and PV.
- **Mount.** The kubelet on the Pod's node does the mount; for CSI it goes through the driver (`NodeStageVolume`/`NodePublishVolume`) and the attach/detach machinery if the driver needs attachment.
- **Deletion.** Claim deleted → `Delete` policy → the provisioner gets `DeleteVolume` (or removes its directory) and the PV object is removed; `Retain` policy → PV goes `Released` and waits for you. Finalizers (`kubernetes.io/pvc-protection`, `kubernetes.io/pv-protection`) stop deletion while things are still in use.

## 3. How it works (diagram)

```mermaid
sequenceDiagram
    autonumber
    actor U as User
    participant A as API server
    participant C as PV controller (kcm)
    participant S as Scheduler
    participant P as Provisioner
    participant D as Storage backend (CSI driver)
    participant K as Kubelet (Pod's node)

    U->>A: create PVC (storageClassName: wffc-fast)
    A->>A: DefaultStorageClass admission fills class if empty
    C->>U: PVC Pending — WaitForFirstConsumer
    U->>A: create Pod that mounts the claim
    A->>S: schedule the Pod
    S->>A: picks node w1; annotates PVC selected-node=w1
    C->>P: claim + selected-node observed
    P->>D: CreateVolume(size, node w1 topology)
    D-->>P: volume created (dir/disk) + handle
    P->>A: create PV object (source + nodeAffinity=w1)
    C->>C: bind PVC <-> PV (Bound)
    K->>D: mount volume on w1
    K-->>U: Pod Running, data dir mounted
```

Walkthrough:

1. The claim alone does nothing when the class uses `WaitForFirstConsumer` — the claim sits `Pending` on purpose (step 3). With `Immediate`, steps 4–7 would run at once and skip the scheduler.
2. The scheduler's pick is recorded on the claim as the `selected-node` annotation; that note is what makes the volume land on the right node.
3. The provisioner — not `kube-controller-manager` — creates both the real storage and the PV object.
4. Binding is then the ordinary PV↔PVC match from [T4.15](../part4-cka/T4.15-manage-persistent-volumes-and-persistent-volume.md); the kubelet mounts last, when the Pod starts.

### 4.2 Declarative YAML

The class and claim from the spec — a `rancher.io/local-path` class that keeps data (`Retain`), waits for the Pod (`WaitForFirstConsumer`) and allows expansion (`allowVolumeExpansion: true`), plus a claim that uses it:

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-local                     # name claims put in spec.storageClassName
  annotations:
    storageclass.kubernetes.io/is-default-class: "false"   # set "true" or patch later; keep ONE default
provisioner: rancher.io/local-path     # who creates volumes — must match a running provisioner; immutable
reclaimPolicy: Retain                  # PVs created from this class keep data on claim deletion (default: Delete)
volumeBindingMode: WaitForFirstConsumer # provision on the node the Pod lands on (default: Immediate)
allowVolumeExpansion: true             # permit claim growth — only honoured if the driver can resize
mountOptions: []                       # mount flags copied to created PVs; not validated; omit if unused
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data
  namespace: lab-t416                  # claims are namespaced
spec:
  storageClassName: fast-local         # "" = no class (static only); omit = use the default class
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi                     # requested size; the provisioner creates a volume of this size
```

A CSI class for reference — same shape, different provisioner and real `parameters` (the driver must exist in the cluster; values are examples):

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: gold-disk
provisioner: ebs.csi.aws.com           # AWS EBS CSI driver name = provisioner name
parameters:                            # free-form, driver-defined keys; wrong key -> CreateVolume error
  type: gp3
  iopsPerGB: "10"
  encrypted: "true"
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer  # zone-aware: the disk is created in the Pod's AZ
allowVolumeExpansion: true
```

A class using `allowedTopologies` — volumes may only be provisioned on nodes labelled zone `a`:

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: zone-a-only
provisioner: rancher.io/local-path
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer   # required for topologies to matter on local storage
allowedTopologies:
- matchLabelExpressions:
  - key: topology.kubernetes.io/zone      # nodes need this label; kind/kubeadm nodes usually lack it
    values: ["a"]
```

**Observe `allowedTopologies` on the lab VMs.** kubeadm nodes carry no zone labels, so label one worker and the class can only pick it — this demo needs the namespace and the `w1`/`w2` names from the lab environment:

```bash
k label node w1 topology.kubernetes.io/zone=a          # on kind: k label node lab-worker topology.kubernetes.io/zone=a
k create ns lab-t416
cat <<'EOF' | k apply -f -          # the zone-a-only class above, plus claim + consumer Pod

allowedTopologies:
- matchLabelExpressions:
  - key: topology.kubernetes.io/zone
    values: ["a"]
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata: {name: topo-check, namespace: lab-t416}
spec:
  storageClassName: zone-a-only
  accessModes: [ReadWriteOnce]

---

spec:
```

**Observe `mountOptions`.** The field is patchable and is copied verbatim onto every PV the class creates afterwards — set it, provision one throwaway claim, and read it back off the PV:


A bogus value passes `apply` silently and only fails when the kubelet mounts the volume: the Pod stalls in `ContainerCreating` and `k describe pod` shows a mount error (the matching row is in section 6). Whether local-path's hostPath-style PVs enforce mount options the same way is in To verify — drivers that honour them (NFS, most CSI drivers) fail loudly.

## 6. Common mistakes and how to fix them

Troubleshooting path for a `Pending` dynamic claim (in order):

1. `k get pvc -n <ns>` — `Pending`? `k describe pvc <name> -n <ns>` and read the Events bottom-up.
2. Event `WaitForFirstConsumer` → create the Pod; done.
3. Event `ExternalProvisioning` looping → check the provisioner named in the message: does a class field really say that name? Are its Pods up? `k get pods -A | grep <provisioner>`, then read its logs (2.10).
4. Event `ProvisioningFailed` → read the driver error in the message and the provisioner logs.
5. Event `storageclass.storage.k8s.io "<name>" not found` → the claim names a class that does not exist; the PVC's class cannot be edited — delete and recreate the claim, or create the missing class.

| Symptom | What you will see | Cause | Fix |
|---|---|---|---|
| PVC `Pending` right after creation | `k describe pvc`: `Normal WaitForFirstConsumer ... waiting for first consumer to be created before binding` | The class uses `volumeBindingMode: WaitForFirstConsumer` — this is expected | Not an error. Create the Pod that mounts the claim; provisioning and binding follow scheduling. |
| PVC `Pending`, provisioning never starts | `k describe pvc`: `Normal ExternalProvisioning ... waiting for a volume to be created, either by external provisioner "rancher.io/local-pat" or manually created by system administrator`, repeating forever | The class's `provisioner` names a provisioner that does not exist (typo) or whose Pods are down (field is immutable) | Check `k get sc <name> -o jsonpath='{.provisioner}'` against running Pods (`k get pods -A \| grep provisioner`). Wrong name: `k delete sc <name>` and recreate correctly. Pods down: fix the provisioner Deployment and read its logs. |
| Claims land in the wrong class | `k get sc` shows `(default)` on **two** classes; a PVC with no `storageClassName` got the newest default | Two StorageClasses carry `is-default-class: "true"` | Remove one: `k patch sc <extra> -p '{"metadata":{"annotations":{"storageclass.kubernetes.io/is-default-class":"false"}}}'`. Verify `k get sc` shows `(default)` once. Claims already stamped keep their class — recreate them if wrong. |
| Pod `Pending`/`ContainerCreating` because its local volume is on another node | Pod events about volume node affinity or failed mount; PV's `nodeAffinity` names a different node than the Pod's | Class bound `Immediate`: the volume was provisioned before the scheduler chose the Pod's node | Recreate the class with `volumeBindingMode: WaitForFirstConsumer` (field is immutable), delete claim and Pod, re-apply. |
| `storageclass.storage.k8s.io "<name>" not found` on the claim | Claim `Pending`; event names the missing class | PVC `storageClassName` has a typo, or the class was deleted; a claim's class cannot be edited | `k get sc` for real names; delete and recreate the claim with the right class, or (re)create a class with the referenced name. |
| Editing claim size is rejected or never finishes | API error on edit, or PVC condition stuck at `Resizing`/`FileSystemResizePending` with no progress | `allowVolumeExpansion` not `true`, or the driver cannot resize (local-path cannot) | Check `k get sc <name> -o jsonpath='{.allowVolumeExpansion}'`; `k patch sc <name> -p '{"allowVolumeExpansion":true}'`. If the driver lacks resize support, create a bigger claim and copy the data instead. |
| Provisioner errors invisible in `k describe pvc` | `ProvisioningFailed` event with a short driver message | The real error is only in the provisioner's log | `k -n local-path-storage logs deploy/local-path-provisioner`, or `k -n <driver-ns> logs <pod> -c csi-provisioner` for CSI. |
| Pod `Pending`: `pod has unbound immediate PersistentVolumeClaims` | Scheduler event on the Pod | The Pod references a claim that has not bound yet (often a knock-on of the rows above) | Fix the claim first, then the Pod schedules. For a WFFC claim this message should not appear — the claim stays `Pending` instead. |
| Bad `mountOptions` on the class | Pods `ContainerCreating` with mount errors in `k describe pod` | `mountOptions` are not validated at apply time | Fix the field on the class (`mountOptions` is patchable), delete the Pod so it remounts; PVs created earlier may need the mount flag fixed individually (see To verify). |

### 7.2 Medium: two classes, Retain vs Delete — compare what deleting a claim does

**Setup.**

```bash

```

**Task.** In namespace `lab-t416` create claims `c-keep` and `c-drop` (each 60Mi, RWO, classes `sc-keep` and `sc-drop` respectively) and Pods `p-keep` and `p-drop` (`busybox:1.36`, each mounts its claim at `/data` and writes a marker file `/data/whoami` containing `keep` or `drop`, then `sleep 3600`). Wait for both claims to bind. Save the two bound PV names, one per line, to `/root/lab/t416/pvs.txt` (keep first). <details><summary>Hint 1</summary>

</details>
<details><summary>Hint 2</summary>

Delete the Pods **before** the claims — a claim in use by a Pod is held by a finalizer.
</details>
<details><summary>Hint 3</summary>

`Retain` leaves the PV `Released` with `claimRef` intact; to fully reset you'd clean the provisioner's data dir on the node and clear `claimRef`. `Delete` makes the provisioner remove the backing directory and the PV object. </details>

<details><summary>Solution</summary>

### 7.3 Break-fix: two defaults and a claim that never provisions

**Setup.** A working default class must exist first (the `local-path` default from Lab 7.1 on the VMs; `standard` on kind — substitute its name where `local-path` appears). Save the script as `break.sh` and run it.

```bash
mkdir -p ~/lab/t416 && cd ~/lab/t416
cat > break.sh <<'EOS'

cat <<'EOF' | kubectl apply -f -
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: bf-fast
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"
provisioner: rancher.io/local-pat
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: bf-claim
  namespace: lab-t416

  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 80Mi
---
apiVersion: v1
kind: Pod
metadata:
  name: bf-pod
  namespace: lab-t416
spec:
  containers:
  - name: c
    image: busybox:1.36
```

Broken state: `bf-claim` is `Pending`, `bf-pod` is `Pending`, and `k get sc` shows two `(default)` entries.

**Task.** In namespace `lab-t416`, claim `bf-claim` never binds, so Pod `bf-pod` never runs. The claim and the Pod belong to the application team: do not delete, recreate or edit either one, and do not change the claim's requested size. Make `bf-claim` bind and `bf-pod` reach `Running`. When finished, the cluster must have exactly one default StorageClass, and a new claim created without `storageClassName` must land in the class that was the default before this incident (`local-path` on the VMs, `standard` on kind). You may delete and recreate the `bf-fast` StorageClass.

<details><summary>Hint 1</summary>

`k describe pvc bf-claim -n lab-t416`, then `k get pvc bf-claim -n lab-t416 -o jsonpath='{.spec.storageClassName}'`. The admission plugin already stamped a class name onto the claim — which class did it pick, and why that one?
</details>
<details><summary>Hint 2</summary>

Two separate faults. One explains why the claim picked `bf-fast`. The other explains why `bf-fast` will never provision — compare `k get sc bf-fast -o jsonpath='{.provisioner}'` with the provisioner that actually runs in the cluster (`k get sc local-path -o jsonpath='{.provisioner}'`, `k -n local-path-storage get pods`).
</details>
<details><summary>Hint 3</summary>

The claim's class field cannot be edited and you may not recreate the claim, so the class `bf-fast` must exist under that exact name with a working provisioner. Most StorageClass fields are immutable — fix by deleting and recreating the class object. Do not carry the default annotation over.
</details>

<details><summary>Solution</summary>

Diagnosis:

```bash
k get pvc bf-claim -n lab-t416 -o jsonpath='{.spec.storageClassName}{"\n"}'   # bf-fast — stamped by DefaultStorageClass admission
k get sc                                        # two "(default)" classes: local-path and bf-fast
k describe pvc bf-claim -n lab-t416 | tail -8
# events loop: ExternalProvisioning ... waiting for a volume to be created, either by
# external provisioner "rancher.io/local-pat" or manually created by system administrator
k get sc bf-fast -o jsonpath='{.provisioner}{"\n"}'      # rancher.io/local-pat
k get sc local-path -o jsonpath='{.provisioner}{"\n"}'   # rancher.io/local-path
k -n local-path-storage get pods                        # the real provisioner runs here
```

Two faults: (1) `bf-fast` is annotated as a **second default**, and since it is the most recently created default, the admission plugin stamped `bf-fast` onto `bf-claim`. (2) `bf-fast`'s `provisioner` is `rancher.io/local-pat` — a typo for `rancher.io/local-path` — so no provisioner ever picks the claim up; the `ExternalProvisioning` event loops forever.

Fix: `provisioner` is immutable, so recreate the class — same name (the claim already points at `bf-fast`), correct provisioner, **without** the default annotation:

```bash
k delete sc bf-fast
cat <<'EOF' | k apply -f -
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: bf-fast
provisioner: rancher.io/local-path        # correct name this time
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
EOF
k get sc                                  # exactly one "(default)": local-path
k wait --for=jsonpath='{.status.phase}'=Bound pvc/bf-claim -n lab-t416 --timeout=120s
k wait --for=condition=Ready pod/bf-pod -n lab-t416 --timeout=120s
k exec bf-pod -n lab-t416 -- cat /data/state.txt        # fixed
```

Why this order: removing the bad default does not un-stamp the claim — `bf-claim` already says `bf-fast`. Deleting the class while the claim references it would turn the error into `storageclass.storage.k8s.io "bf-fast" not found`, so the class must come back under the same name with the working provisioner. Leaving the default annotation off `bf-fast` restores `local-path` as the single default (the annotation's absence, not `"false"`, is also fine as long as only one class shows `(default)`).
</details>

**Verification.**

```bash

test "$(k get pod bf-pod -n lab-t416 -o jsonpath='{.status.phase}')" = "Running" && echo OK2
test "$(k exec bf-pod -n lab-t416 -- cat /data/state.txt)" = "fixed" && echo OK3
```

## 8. Exam tips

- Open https://kubernetes.io/docs/concepts/storage/storage-classes/ and copy the example class — edit the four lines that matter (`name`, `provisioner`, `reclaimPolicy`, `volumeBindingMode`). https://kubernetes.io/docs/concepts/storage/dynamic-provisioning/ explains the default-class behavior; https://kubernetes.io/docs/tasks/administer-cluster/change-default-storage-class/ is the step-by-step for switching defaults. All three are allowed exam docs.
- `k get sc` is the fastest status board: it shows `PROVISIONER`, `RECLAIMPOLICY`, `VOLUMEBINDINGMODE`, `ALLOWVOLUMEEXPANSION` and `(default)` in one line per class. Run it before **and** after any class task; tasks that say "make X the default" implicitly require removing the mark from the old one — verify exactly one `(default)` remains.
- Remember the immutability trap: you cannot patch a wrong `provisioner`, `parameters`, `volumeBindingMode`, `allowedTopologies` or `reclaimPolicy`. Delete the class and recreate it — claims that already reference the name then provision normally. You *can* patch `allowVolumeExpansion`, `mountOptions` and annotations.
- A `Pending` claim with `WaitForFirstConsumer` in its events is finished work waiting on a Pod, not a failure. Do not burn exam minutes "fixing" it — create the consumer Pod.
- Three cases for the claim's class field: a name = that class, `""` = static only, field omitted = default class. Tasks that say "must not use dynamic provisioning" want `storageClassName: ""`.
- Pace: the exam has 15-20 tasks in 2 hours (https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad and https://docs.linuxfoundation.org/tc-docs/certification/faq-cka-ckad-cks). A "create class + claim + Pod" task should take a few minutes: `k explain storageclass` jogs field names without a browser.

<details><summary>Answers</summary>

1. `k get sc`. The `(default)` suffix in the `NAME` column; the `VOLUMEBINDINGMODE` column (`Immediate` or `WaitForFirstConsumer`).
2. `k patch sc local-path -p '{"metadata":{"annotations":{"storageclass.kubernetes.io/is-default-class":"true"}}}'`; then `k get sc | grep -c '(default)'` must be `1` (remove the annotation from any other class first).
3. Node-local volumes only exist on one node, so the volume must be created where the Pod will run. WFFC delays provisioning until the scheduler picks a node and writes `volume.kubernetes.io/selected-node` on the claim; the provisioner creates the volume for that node.
4. Admission stamps the default class when the PVC omits `storageClassName` entirely — an explicit `storageClassName: ""` is left classless on purpose → for WFFC the scheduler picks a node → the external provisioner calls `CreateVolume` on the driver → the provisioner creates the PV object → the PV controller binds claim and PV → the kubelet mounts it into the Pod.
5. Compare the provisioner name in the event with `k get sc <class> -o jsonpath='{.provisioner}'` and with the provisioners actually running (`k get pods -A | grep provisioner`). Name wrong → recreate the class (field is immutable). Pods down → fix/read `k -n local-path-storage logs deploy/local-path-provisioner` (or the driver's `csi-provisioner` container). Only then re-read the claim's events.
6. The provisioner deletes the backing storage (`DeleteVolume` / removes the directory), then the PV object is deleted — data destroyed. With `Retain` the PV would go `Released`, keep `claimRef` and keep the data until you clean it and clear `claimRef` or delete the PV.
7. `""` means "no class — static binding only". Omitting the field means "ask admission for the default class" (and PVCs created while no default exists are updated retroactively when one appears).
8. `data-web-0`, `data-web-1`, `data-web-2`. They are kept (with their PVs and data) after StatefulSet deletion — delete the PVCs by hand to reclaim.
9. `provisioner` is immutable after creation. Fix: `k delete sc <name>` and recreate with the correct value — keep the same name if claims already reference it. Patchable: `allowVolumeExpansion`, `mountOptions`, labels/annotations.
10. A `VolumeAttributesClass` (GA v1.34) holds driver-tunable parameters (e.g. IOPS) applied to an existing volume via `volumeAttributesClassName` — it can be swapped on a live claim if the driver supports `ModifyVolume`. A StorageClass is chosen at provisioning time, decides who creates the volume and with what fixed parameters.
</details>
